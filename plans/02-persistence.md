# Phase 2 — Persistence Foundation

## Context / problem

The application needs durable relational storage with constraints that support CRUD, atomic multi-test orders, historical correctness, and useful filtering. Local development should use the installed Turso CLI without a hosted account while retaining a direct path to Turso Cloud deployment.

## Approach

Use Drizzle with `@libsql/client` against a `turso dev` server persisted to an ignored local database file. Add a root `db:dev` command and include the Turso process in the eventual `bun dev` orchestration. Configure the application via `TURSO_DATABASE_URL` and optional `TURSO_AUTH_TOKEN`: local development points to the unauthenticated localhost Hrana endpoint, while cloud deployment changes only environment values. Use isolated temporary local libSQL databases for fast integration tests rather than sharing the developer server. Define explicit tables for patients, lab tests, orders, and order tests. Use text UUIDs generated by the application, UTC ISO timestamps at API boundaries, integer cents, foreign keys, checks where Drizzle/SQLite supports them cleanly, and compound indexes matching filters plus cursor sort/tie-break columns. Commit generated migrations and provide an idempotent deterministic seed.

Snapshot test code/name/price/turnaround on `order_tests`, and persist `orders.total_cents` plus `estimated_ready_at` as facts established at creation.

## Acceptance criteria

- `turso dev` persists local data in an ignored file and requires no hosted account or auth token.
- The API uses environment-configured libSQL URL/token values, so a future Turso Cloud database requires configuration—not persistence-layer changes.
- `bun dev` starts Turso, API, and web together; DB-only development is available through `bun run db:dev`.
- Lab test code uniqueness is enforced by SQLite, not only application code.
- Required relationships and values are non-null and foreign keys are enforced.
- Money is integer cents; turnaround is positive integer elapsed hours.
- An order cannot contain the same catalog test twice.
- Compound query indexes support patient name search/sort, test code/name/active narrowing, and orders by patient/status plus cursor ordering.
- Migration works from empty state and seed demonstrates every primary screen.
- Test suites use isolated temporary libSQL databases and never contact or mutate the developer Turso database.
- Database invariants have executable integration tests written before their schema implementation.

## Verification

- `bun run db:generate` reports no uncommitted schema drift after migration generation
- Start `bun run db:dev`, migrate its empty local Turso database with `bun run db:migrate`, and verify API connectivity
- Run `bun run db:seed` twice against local Turso and verify deterministic results
- Run `bun dev` and confirm Turso/API/web processes start and stop together
- Point configuration validation at a cloud-shaped `libsql://` URL/token without requiring an actual hosted database
- Inspect constraints/indexes and exercise a foreign-key/unique-code failure
- Run isolated DB helper tests
